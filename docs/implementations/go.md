# Go Implementation

## Overview

Go is a per-language implementation of this playbook's principles using just the standard library (`net/http`, `database/sql`) plus a minimal set of third-party dependencies.
The guide and runnable examples implementing this playbook's principles with Go live in `implementations/go/` in this repo.

**→ [implementations/go/docs/architecture/](../../implementations/go/docs/architecture/)** — of the root's 24 `docs/architecture/*` docs, 21 have a corresponding Go implementation detail doc (Strategic Design is language-agnostic so the root doc is referenced as-is; for domain-service, the root doc already cites nestjs's code as its real example, so Go doesn't have a separate doc either, but the table below cites Go's own code; cross-domain-communication is covered by [`cross-domain.md`](../../implementations/go/docs/architecture/cross-domain.md))
**→ [implementations/go/examples/](../../implementations/go/examples/)** — full implementation example of the three Account/Card/Payment Bounded Contexts (account open/deposit/withdraw/suspend/reactivate/close + email notifications, card issue/suspend/close, card payment/payment cancellation/refund)
**→ [implementations/go/harness/](../../implementations/go/harness/)** — automated evaluator that checks guide compliance

This doc maps how much, and how, the Go implementation (21 `docs/architecture/*.md` docs + the `examples/` code + `harness/`) covers each of the root's 24 `docs/architecture/*` docs. **The level of documentation and whether the `examples/` code actually follows the principle are two separate things.** Where a doc explains the correct pattern while still noting a gap in the current code (e.g. file storage having no example use case), that's left as-is in the Notes column below.

## What the harness actually verifies / doesn't verify

`implementations/go/harness/main.go` (184 lines — the per-rule logic lives in one file per rule) registers 28 rules. They span both structure/placement and a substantial set of semantic checks:

- **Structure/placement**: `snake_case.go` file naming, the `internal/{domain,application,infrastructure,interface}` + `application/{command,query}` directories, Repository interface under `domain/` with its implementation under `infrastructure/`, Handler/Event Handler/Integration Event/Task Controller/Scheduler placement, dedicated `outbox/`/`task-queue/` directories
- **Layer isolation**: no framework/infrastructure imports in `domain/` (`domain-layer-isolation`), no logging in `domain/` (`no-logging-in-domain`), no infrastructure imports in `interface/` (`interface-no-infrastructure`), no direct `os.Getenv` outside `config/` (`no-direct-env-access`), Scheduler in infrastructure only
- **Cross-BC boundaries**: `no-cross-aggregate-reference`, `no-cross-bc-domain-import`, `no-cross-bc-repository-in-application`
- **Semantic rules**: Repository method naming (`repository-naming`: `Find<Noun>s`/`Save<Noun>`/`Delete<Noun>`, blocking `FindBy*`/`Update*` etc.), Query Handlers never referencing a write-capable Repository (`cqrs-pattern`) and never returning a raw Aggregate (`query-handler-no-raw-aggregate`), typed sentinel errors only (`typed-errors-only`), the standard `{statusCode, code, message, error}` error-response schema (`error-response-schema`), no generic `result`/`data`/`items` response keys, the soft-delete filter on lookups (`soft-delete-filter`), the hyphen-free 32-char hex Aggregate ID format (`aggregate-id-format`), no synchronous outbox draining (`outbox-drain-order`), rate-limit middleware actually wired (`rate-limit-wired`), Dockerfile conventions, swag OpenAPI annotations on every HTTP handler (`api-documentation`), no silently-swallowed errors (`no-silent-catch`)

See `implementations/go/harness/README.md` for the full rule table. What the harness does NOT catch:

- Whether Domain/Application unit test files exist (test presence/coverage isn't checked at all)
- Business-rule correctness — whether an invariant check is right, or whether logic sits in the semantically correct layer for its domain meaning (per `docs/harness.md`, deliberately out of scope: the harness never assumes business-domain knowledge)
- Transaction-boundary correctness — e.g. whether a multi-Aggregate write actually uses `database.WithTx`
- Doc/code drift inside prose documents (that's `scripts/check_docs_drift.py`'s job, not the harness's)

## Go-specific, no corresponding root doc

- **Compile-time interface-satisfaction verification** — the `var _ order.Repository = (*OrderRepository)(nil)` idiom. Unlike TypeScript's structural typing or NestJS's DI-token binding, Go gets static safety from this pattern — "if the implementation doesn't satisfy the interface, compilation itself fails." None of the root docs mention this kind of compile-time verification mechanism.
- **Package-level encapsulation** — Go has no instance-level `private` (see `tactical-ddd.md`). The root docs don't assume this constraint.
- [`api-documentation.md`](../../implementations/go/docs/architecture/api-documentation.md) — swaggo/swag `@`-annotation-based OpenAPI generation (`go tool swag init`), the committed `docs/` output blank-imported by `main.go`, the `/docs/` Swagger UI route, and the CI step that fails when the committed spec drifts from the annotations.
- [`bootstrap.md`](../../implementations/go/docs/architecture/bootstrap.md) — the dependency-assembly order against the real code in `cmd/server/main.go` (constructor chaining, no DI container), covering logging/tracing setup, three-BC assembly, the outbox/task-queue background loops, and graceful shutdown.
- [`cross-domain.md`](../../implementations/go/docs/architecture/cross-domain.md) — Adapter pattern implementation details (see the root's [cross-domain-communication.md](../architecture/cross-domain-communication.md) for the principle). The three business BCs Account/Card/Payment really exist, so it covers both the synchronous Adapter and the asynchronous Integration Event as real code.
- [`design-principles.md`](../../implementations/go/docs/architecture/design-principles.md) — a 14-item TL;DR checklist condensing the other 27 docs.
- [`module-pattern.md`](../../implementations/go/docs/architecture/module-pattern.md) — given that Go has no DI container, explains how manual constructor assembly and the package tree stand in for NestJS's `@Module`, and the advantage that the Go compiler blocks circular dependencies outright with no workaround like `forwardRef()`.
- [`rate-limiting.md`](../../implementations/go/docs/architecture/rate-limiting.md) — middleware based on `golang.org/x/time/rate`'s token bucket. A global limiter is really implemented in `examples/`, injected into `NewRouter`, and applied across all write routes — a per-client (IP) limiter map, differentiated per-route application, and exposing `X-RateLimit-*` headers remain unadopted extension options (forward-looking) from the doc. An over-limit 429 response follows the same `{statusCode, code, message, error}` JSON schema (`RATE_LIMIT_EXCEEDED`) as other error paths.
- [`shared-modules.md`](../../implementations/go/docs/architecture/shared-modules.md) — the placement convention for shared code like `internal/common/`, `internal/interface/http/middleware/`, etc. Explains that, unlike NestJS's `@Global` module declaration, "sharing" here just means `main.go` passes the same instance to multiple constructors.

## Why Go

- **Standard library first** — `go.mod`'s direct dependencies are the AWS SDK v2 (SES/SQS/Secrets Manager), `google/uuid`, `lib/pq`, `golang-jwt/jwt`, `golang.org/x/crypto` (bcrypt), `golang.org/x/time` (rate limiting), `prometheus/client_golang` (metrics), the OpenTelemetry packages (`go.opentelemetry.io/otel` + `otelhttp` + OTLP/stdout exporters, tracing), `swaggo/swag`/`http-swagger` (OpenAPI), and `testify`/`testcontainers-go` for testing. No web framework, no ORM, no DI container.
- **The structural typing of `interface` fits naturally with Repository/Technical Service abstraction.**
- **CQRS's Handler pattern is expressed with just a struct + methods, no framework.**
- **Static compilation and explicit error handling (returning `error`) pair well with the Domain/Application layers' plain-error principle.**
